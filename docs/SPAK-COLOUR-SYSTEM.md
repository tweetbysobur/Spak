# SPak Colour System

Version 1.0. Source of truth: `src/design/colors.json`, generated by `scripts/brand/build_colors.py`. Tests: `tests/brand/contrast.test.ts`.

Brand colours are fixed inputs. Every other colour was **computed**: it is the lightest (light theme) or darkest (dark theme) shade of its hue that meets its WCAG target against **every** surface it may appear on, plus a 0.25 safety margin. No value was picked by eye.

WCAG 2.x minimums used: normal text 4.5:1. Large text (24 px, or 18.66 px bold) 3:1. Meaningful graphics and UI component boundaries 3:1.

## 3. Semantic status colours

Eight roles. The six you requested, plus two that SPak's real states need:
- **refunded**: a verified refund is a good outcome, but it is not a completed transfer, so it never uses the success colour.
- **neutral**: cancelled, expired before deposit and draft are neither failures nor successes.

Each role has foreground (labels and text), background (tint), border and icon. In the light theme the border and icon are the same 3:1 shade.

Rules built into the mapping (tested):
- `success` is used only for independently verified outcomes: COMPLETED (destination verified) and a deposit CONFIRMED on chain.
- UNKNOWN, refund DELAYED and refund UNKNOWN are `warning`. They never look successful.
- A refund that is only PARTIAL is `warning`, and one still in ASSOCIATION_PENDING is `pending`. Only a verified, completed refund is `refunded`.
- REFUNDING, VERIFYING_DESTINATION and SUBMITTED are `processing`: work is happening. AWAITING_APPROVAL, AWAITING_DEPOSIT and manual review are `pending`: waiting on someone else.

## 6. Usage rules

- **Never rely on colour alone.** Every status needs a text label, plus an icon wherever space allows. Success (green) and refunded (teal), and processing (blue) and info (slate), are close for some colour-vision deficiencies. The label is what tells them apart.
- Processing may animate. Pending never animates, because it is waiting on someone else.
- Status foreground colours are for status labels and inline status text only, not for body copy or links.
- Body links use the primary colour, underlined.
- **Focus ring:** `focusRing`, 2 px wide, with a 2 px offset filled with the page background. Against the primary button itself the ring is 1.00:1, so the offset is required. The ring then contrasts with the page background: light 9.03:1 or better, dark 7.05:1 or better, on every surface.
- Muted Sage: decoration only on light surfaces, such as illustration fills, dividers and the dark-theme logo symbol.
- Forest Green is never placed on Graphite. In dark contexts use Light Forest, or a Warm White or Muted Sage logo.
- The hairline `border` tokens are decorative. Anything a user must perceive to operate (input edges, toggle tracks, selected states) uses `borderStrong` or a semantic border.

### Correct

- Graphite body text on Warm White (14.02:1). Deep Sage descriptions under it (5.14:1).
- A "Completed" badge: success foreground on success tint, with a check icon and the word "Completed".
- A "Refunded" badge: teal, with a return-arrow icon and the word "Refunded". Never green, never a check mark.
- An "Unknown or delayed" badge: warning amber, with a clock or alert icon and the label.
- Dark theme primary button: Light Forest background, Graphite label (8.31:1 or better across rest, hover and active).

### Incorrect

- Muted Sage helper text on Warm White (1.94:1).
- A Forest Green button on a Graphite page (1.44:1).
- Showing UNKNOWN or a partial refund in green.
- Using the success colour for REFUNDED.
- A coloured dot with no label as the only status indicator.
- Using the decorative hairline border for an input field.

## 8. Limitations

- Contrast is calculated with the WCAG 2.x formula. APCA (proposed for WCAG 3) was not calculated.
- Colour-vision deficiency was not simulated. The label and icon rules cover it, but success vs refunded and processing vs info are close for some deficiencies.
- Print values (CMYK, Pantone) are not defined.
- The app does not use these tokens yet. Applying them (Tailwind or CSS variables) is a separate task.
- Disabled tokens are deliberately low contrast and should be paired with a "not available" explanation where it matters.
